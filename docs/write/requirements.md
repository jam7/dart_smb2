# 要件: ファイルの書き込み

- 作成: 2026-08-15 / 状態: approved (P1、2026-08-15 に実サーバーで確認)
- 背景: このライブラリは読み取り専用として作られ、書き込みは Phase 2 として
  README に予告されていた。image-viewer が持っているファイルを共有へ戻す用途が
  決まったので、その最小限を実装する。**読み取り専用であること自体が今の
  安全性の一部**だったので、それを外す変更として扱う。

## この文書が決めていること、決めていないこと

ここで決めるのは**プロトコルの 1 操作に対応する道具**だけで、それを**どう
組み合わせるかは決めない**。

たとえば「一時名で書き、書き終えてから正規の名前へリネームする」は、中断に
備える良い作戦だが、**ライブラリの仕事ではない** (2026-08-15 に決定):

- 頼まれていないパスに書くことになり、低レベルのクライアントとしては驚きが大きい
- **プロセスごと落ちたときの一時ファイルを、ライブラリは片付けられない**。
  次回起動で掃除できるのは、自分の命名規則と置き場を知っている呼び出し元だけ
- 呼び出し元が既に同じ作戦を持っていれば二重になる

作戦の一部しか持てないものが「安全な書き込み」という名前を持つと、実際より
安全に見える。だからここでは**材料を揃え、作戦は呼び出し元に委ねる**。

## 段階

書き込みは 1 度に作らない。区切りは**「終わったときに呼び出し元が何をできるか」**
で、プロトコルのメッセージ単位ではない。**この文書が決めるのは P1 だけ**で、
後段は順序の合意として書いてある (2026-08-15)。

| | 呼び出し元ができること | 加わる API | コードに現れる disposition |
|---|---|---|---|
| **P1** | 共有に新しいファイルを 1 本置く。既にあれば置かずに失敗する | `createNew` → `Smb2FileWriter` (`write` / `close` / `written`) | `FILE_CREATE` のみ |
| **P5** | 同じことを速く | (変更なし。内部で並列化) | 同上 |
| **P2** | 中断に備える — 別名で書いて、書き終えてから名前を変える | `rename` / `delete` | 同上 + SET_INFO 2 種 |
| P3 | 既存を編集する — 追記、途中書き、切り詰め | `openForAppend` / `openForUpdate` / `truncate` | + `FILE_OPEN` ほか |
| P4 | 入れ物と属性 | `createDirectory` / `deleteDirectory` / `setTimes` | |

進める順は **P1 → P5 → P2** (2026-08-15 に合意)。P3 以降は未定。

**P5 は一度「不要」と判断しかけたが、測った場所が違ったので保留に戻した**
(2026-08-15):

```
有線 LAN:  write 64MB = 91.7 MB/s (直列)、read = 105.3 MB/s (並列)
```

有線では直列が読みの 87% に達しており、並列化の余地は 13% しか無い。
**しかしアプリが実際に動くのは WiFi のタブレット**で、README の読み取り実測が
その差を示している — **並列化の効きは有線 1.18 倍に対し WiFi は 1.76 倍**
(50 → 88 MB/s)。並列化が隠すのは往復遅延で、有線には隠すべき遅延がほとんど無い。

したがって **P5 の可否は WiFi で測るまで未決**。有線の数字で一般化したのが
誤りだった。

判断の材料としてもう一方も書いておく。P5 をやると増えるもの:
失敗時の穴、`written` の意味の再定義 (「連続して書けた長さ」)、
後始末できない中途半端なファイル。**WiFi で 1.5 倍以上出るなら見合う**、
というのが今の見立て。

**P1 を終えた時点で、このライブラリに利用者のファイルを消す経路は 1 本も無い。**
上書きも削除もリネームも入っていないため。これが P1 の線を引いた基準。

差し替え (`replace`) は作らない。**新しい名前で書いてから rename すれば済む**ので、
上書き用の disposition を持つ理由がない。

## 要件一覧

### R-01: 新しいファイルを作って中身を書ける
- 内容: 呼び出し元が、共有上の指定したパスに新しいファイルを作り、
  与えたバイト列をその中身にできる
- 入出力例: 入力 `books/vol2.zip` と 12,345,678 バイト →
  出力: 共有上に同じ名前・同じ長さのファイルができ、読み直すと同じ中身
- 境界条件:
  - **0 バイト**: 中身のないファイルができる (エラーではない)
  - **サーバーの 1 回の書き込み上限を超える大きさ**: 分割して送る。
    呼び出し元は分割を意識しない
  - **親ディレクトリが無い**: 失敗する。ディレクトリは作らない
  - **書き込み権限が無い**: 失敗し、権限の問題だと分かる形で報告する
  - **途中で失敗した**: そこまで書けたものが共有に残る。**消しに行かない** —
    後始末は呼び出し元の作戦の一部で、何バイト書けたかは報告する
- 優先度: must

### R-02: 既にあるファイルには書けない
- 内容: 書き込み先に既にファイルがあるとき、**失敗する**。この段階には
  上書きする手段そのものが無い
- 入出力例: 入力: 既にある `books/vol2.zip` へ書き込み →
  出力: 例外。ファイルは元のまま (長さも中身も変わらない)
- 境界条件:
  - 存在判定と作成の間に他者が作った場合も失敗する。
    **判定してから作るのではなく、サーバーに「無ければ作れ、あれば失敗しろ」と
    言わせる** ([MS-SMB2] 2.2.13 の CreateDisposition = `FILE_CREATE`) ので、
    確認と作成の間に競合の窓が無い
  - 同じ名前のディレクトリがある場合も失敗する
- 優先度: must

### R-03: どこまで書けたかを後から読める
- 内容: 書き込みが終わったあと (成功でも失敗でも)、**何バイトがサーバーに
  渡ったか**を呼び出し元が読める
- 入出力例: 入力: 100MB の書き込みが 30MB で失敗 →
  出力: 例外。そのあと `written` が 30MB 前後を返す
- 境界条件:
  - 成功したときは、渡したバイト列の長さと一致する
  - **進行中の通知は作らない**。分割するのは呼び出し元なので、渡した量は
    呼び出し元が既に知っている。巨大なバッファを 1 回で渡す使い方が出てきたら、
    そのとき通知を足す (追加は非破壊)
- 優先度: must

## 非機能要件

- **性能**: 読み取りが LAN で 110MB/s 出ているのに対し、書き込みは
  **まず正しさを優先**する。1 本ずつ直列に送る形から始め、速度が問題に
  なってから並列化を検討する (読み取りも最初は直列だった)
- **互換性**: 既存の読み取り API は 1 行も変えない。書き込みは追加される
  メソッドとして入る。`Smb2Tree` を使っている既存コードは影響を受けない
- **対応環境**: SMB 2.0.2 / 2.1 / 3.0。署名・暗号化は使わない (README の Scope)
- **制約**:
  - **read-only であることが安全性の一部だった**。これを外す以上、既定値は
    安全側に倒す (R-02)
  - 検証は**実サーバーでしかできない**。偽サーバー相手の単体テストは
    「書けたつもり」を通してしまう

## やらないこと (スコープ外)

- **上書きする手段そのもの**。`FILE_SUPERSEDE` / `FILE_OVERWRITE` /
  `FILE_OVERWRITE_IF` はこの段階のコードに現れない。既にあるものを差し替えたく
  なったら、新しい名前で書いてから rename する (P2)
- 追記、途中からの書き込み、途中再開
- 書き込み中の進捗通知 (R-03 のとおり、`written` で足りる)
- **リネームと削除** (2026-08-15 に決定: この段階では作らず、後で足す)。
  したがって呼び出し元は**正規のパスへ直接書く**ことになり、途中で失敗すれば
  中途半端なファイルがそのパスに残る。フェーズ 1 はそれを受け入れる。
  だから R-01 の「何バイト書けたか」が後始末の唯一の手がかりになる
- **一時名で書いてリネームする作戦**、およびそれに類する後始末つきの
  「安全な書き込み」。材料を揃えたうえで、組み立ては呼び出し元の仕事
- ディレクトリの作成と削除、属性・タイムスタンプの変更、ロック
- 書き込みの並列化 (非機能要件のとおり、まず直列)
- image-viewer 側の画面・操作。ライブラリの範囲だけを決める

## 奪う既定動作

このライブラリを使うだけでは**共有のデータが壊れようがなかった**。書き込みが
入ると、バグ 1 つで利用者のファイルが失われうる。代わりに用意するもの:

- 既定で既存を壊さない (R-02)。判定するのはサーバーなので、
  確認してから書くまでの競合の窓が無い
- 失敗したとき、**何バイト書けたか**を報告する (R-01)。呼び出し元が
  後始末を決められる材料
- 検証を実サーバーで行う (非機能要件の制約)
